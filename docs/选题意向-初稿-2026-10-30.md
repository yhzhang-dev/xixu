## 一、选题背景与原型现状

### 1.1 选题来源

个人在日常生活中产生的数据（消费流水、课程安排、日程待办、每日记录、凭证截图）长期散落在多个应用中，彼此割裂，难以统一检索与统计。本人在日常使用本地 AI 助手工具的过程中，接触到聊天接入、长期记忆、定时任务等能力，并曾编写角色卡（AGENT.md）一类配置；同时受 Muse 等个人助手类产品启发，认识到"能够记住用户、并主动提供服务"的助手，比通用聊天框更具实用价值。

基于这一判断，本人使用 Python 脚本与 Markdown / JSONL 文件，搭建了一个可运行的个人助手原型，以即时通讯软件作为交互入口，以脚本与语言模型作为业务处理逻辑，自 2026 年 10 月起在日常使用中持续迭代（约两周、29 次提交）。

### 1.2 原型已实现的功能

| 能力 | 实现方式 | 现状 |
|---|---|---|
| 记账 | 聊天中一句话或凭证截图 → 解析入账；支持月报、更正留痕、作废 | 8 个子命令，账目持续记录中 |
| 课表 | Markdown 维护 → 自动生成 ICS 日历文件 | 已生成并同步 |
| 每日日志 | 按日期记录，可回看 | 连续 9 天 |
| 附件归档 | 扫描 → 归档 → 写索引 → 校验（sha256 去重、缺文件检测） | 41 个凭据与索引 |
| 长期记忆 | 自我 / 用户 / 共同经历 / 当前关注 + 隐私规则 + 更正记录 | 7 个记忆文件 |
| 主动服务 | 晨信、晚安信定时发送 | 模板与发送状态已落地 |
| 流程工具化 | 每个流程写成可复用脚本与技能说明 | 5 个工具 + 2 个技能 |

### 1.3 原型暴露的问题

原型虽可日常使用，但存在明显局限，也正是本课题要解决的问题：

1. **数据层缺陷**：文件不具备事务、索引与并发控制能力，统计依赖脚本，数据结构调整需人工迁移。
2. **入口受限**：依赖第三方聊天软件，无法提供表单校验、图表展示、离线访问等能力。
3. **一致性缺失**：附件归档依赖脚本与人工补录，索引与文件容易不一致；课表、账本、日志各自维护，存在重复录入。
4. **记忆不可检索**：长期积累的记录与偏好以纯文本存放，无法按时间、标签、实体检索。
5. **单机运行**：仅能在个人电脑上使用，无法多端访问，也无法在移动场景下即时记录。

### 1.4 结论

本课题拟将该"文件 + 脚本 + 即时通讯入口"的原型，重构为一个具备规范数据库设计（20 张表）、多端访问、离线可用与智能录入能力的完整信息系统。原型的价值在于：**它提供了真实的使用场景与数据，使本课题的需求分析不依赖假设。**

## 二、研究内容与优先级

系统分为移动端（Android）、服务端（Web API）与管理后台三部分。考虑到个人独立开发的时间约束，功能按三级优先级交付，**每完成一级，系统均可独立运行**。

| 级别 | 模块 | 主要内容 | 定位 |
|---|---|---|---|
| **P0** | 账本管理 | 收支流水、分类与账户、月度预算、月度报表 | 及格线，必须完成 |
| **P0** | 日程与课表 | 课程/课次维护、调停课、冲突检测、ICS 导出 | 及格线，必须完成 |
| **P0** | 系统管理 | 用户、角色权限、数据字典、操作审计 | 及格线，必须完成 |
| **P0** | 数据层 | 20 张表设计、初始化脚本、数据迁移与备份 | 及格线，必须完成 |
| **P1** | 日志与附件 | 每日记录、标签体系、凭证图片归档（对象存储）、检索 | 提升分数 |
| **P1** | 统计报表 | 多维度统计、图表展示、Excel/PDF 导出 | 提升分数 |
| **P1** | 移动端客户端 | Android：登录、今日时间线、录入表单、图表 | 提升分数 |
| **P2** | 智能录入 | 自然语言解析（"午饭 25"→ 一笔流水）、图像识别、低置信度追问 | 系统亮点 |
| **P2** | 记忆与回顾 | 结构化记忆条目、关键词检索、回答时引用原记录 | 系统亮点 |
| **P2** | 主动服务 | 定时推送：晨间日程、当日回顾、账单提醒 | 系统亮点 |
| **P3** | — | 向量检索、端侧模型、多轮对话、情绪分析 | 明确不做，防止范围失控 |

### 2.1 智能层的边界

本系统**不构建通用 Agent 框架**，只实现"单轮结构化交互"：

- 一条输入 → 一次解析 → 一个明确操作，不做多步任务规划；
- 可用工具固定为四个：记一笔、加日程、查统计、写日志；
- 解析失败或置信度低于阈值时，退回手动表单，不猜测、不重试；
- 模型服务不可用时，系统降级为纯手动录入，核心功能不受影响。

这一边界既是工程约束，也是本课题"轻量级个人助理"的明确定位。

## 三、技术路线

| 层次 | 选型 |
|---|---|
| 移动端 | Android：Kotlin + Jetpack Compose + MVVM + Hilt + Room + Retrofit/OkHttp |
| 服务端 | Java 17 + Spring Boot 3 + MyBatis-Plus + Spring Security + JWT |
| 数据库 | MySQL 8.0（业务数据）+ Redis（缓存/会话/限流） |
| 管理后台 | Vue 3 + TypeScript + Element Plus + ECharts |
| 智能层 | 大模型 API（对话解析）+ OCR（凭证识别），支持本地模型离线兜底 |
| 对象存储 | 阿里云 OSS / 腾讯云 COS（凭证图片、导出文件） |
| 部署 | 云服务器（Linux）+ Docker Compose + Nginx + 自有域名 + HTTPS |

**系统架构**：Android / Web → Nginx → Spring Boot（REST + WebSocket）→ MySQL / Redis / OSS。

## 五、难点与创新点

1. **自由文本 / 图片到结构化数据的解析**：设计带 Schema 约束的解析流程，输出置信度；低于阈值时反问用户而非猜测，保证账目数据"宁可缺失，不可错误"。
2. **历史数据迁移与一致性验证**：将既有 JSONL 账本、Markdown 课表、附件索引导入数据库，设计逐笔比对脚本，验证金额、分类、日期零误差。
3. **离线优先与增量同步**：以 Room 作为移动端唯一数据源，设计基于消息序号与游标的增量同步机制，弱网与断网场景下不丢数据。
4. **可降级设计**：智能录入依赖模型服务，但整体架构保证模型不可用时系统仍可完整运行，降低演示与运行风险。
5. **范围控制**：以 P0→P1→P2 的增量方式交付，确保任一阶段结束时系统完整可用，避免"亮点没做成、基础也没做完"。
