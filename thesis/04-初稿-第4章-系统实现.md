第 4 章 系统实现

本章说明第 3 章的设计在三个工程中的具体实现。服务端按业务域纵向切分，每个业务域由控制器、服务、仓储、请求对象与异常处理器五部分组成，不使用对象关系映射框架，全部 SQL 手写；Web 端是一个单页应用，用状态机而不是路由来组织页面；Android 端是 uni-app 工程，八个页面通过配置文件注册。全章先说明工程结构与工具链，再依次说明认证、记账、日志与训练、身体健康四个模块的实现要点，最后说明客户端实现与只读工具接口。

4.1 开发环境与工程结构

4.1.1 工具链与版本

服务端使用 Java 17 与 Spring Boot 4.1.2，构建由 Maven Wrapper 3.10.0 完成，不要求本机预装 Maven。工程依赖包括 Web 模型视图控制器、Spring Security、参数校验、Spring JDBC 与 Actuator 五个起步依赖，数据库驱动为 MySQL 官方驱动。Web 端使用 Vue 3.5 与 Vite 8，仅有两个运行时依赖，没有引入界面组件库、图表库与类型系统。Android 端使用 uni-app 的 Vue 3 语法，由 HBuilderX 构建并运行到真机。数据库为 MySQL 8.4.13，本地以 Windows 服务方式随系统启动。

4.1.2 三个工程的职责与目录组织

服务端共四十个源文件、一千二百八十八行，按业务域分包：认证包负责登录、会话与请求过滤，记账包负责账目，日志包负责日志与训练组次，健康包负责体重与睡眠，智能工具包负责跨模块只读汇总，基础包只包含健康检查与启动类。每个包内部的文件命名保持一致，控制器只做参数绑定与状态码映射，服务只做校验与流程编排，仓储只做 SQL 与行映射，业务对象以不可变记录类型表示。这一约定使新增一个业务域只需复制一组同名文件，降低了后续扩展的理解成本。

Web 端共七个源文件、一千零六十行，其中主组件七百九十七行、健康面板组件一个、样式文件一个、接口封装四个。接口封装按业务域拆分，与后端的包结构一一对应，便于定位。Android 端共八个页面、一千四百四十一行，页面在配置文件中的顺序决定了启动页，登录页排在首位，其余七个页面覆盖首页、身体与训练、日志与训练、记账的录入与列表。

4.2 统一身份认证的实现

4.2.1 令牌的生成、摘要存储与会话表

登录流程在服务层的一个事务方法内完成。首先按用户名查询用户，若用户不存在、账号状态不为 1，或密码摘要比对失败，三者返回同一个空结果，不区分具体原因，避免通过响应差异枚举用户名。比对通过后，用密码学安全的随机数生成器取三十二字节，做无填充的 Base64URL 编码，得到四十三字符的令牌。令牌本身不落库，落库的是它的 SHA-256 十六进制摘要。会话记录的插入语句直接使用数据库时间函数写入创建时间，并以数据库时间加二十四小时作为过期时间，避免应用服务器与数据库服务器的时钟差异导致过期判断偏移。

在插入会话记录之前，实现先对用户行加排他锁，再统计并保留最近的五个活跃会话，其后的会话按创建时间倒序逐条置为撤销。加锁的目的是让同一用户的并发登录串行化，否则两个并发请求可能各自统计出四个活跃会话，最终留下六个。登录成功后还会清理该用户三十天前已撤销或已过期的会话记录，使会话表的增长有上界。

4.2.2 请求过滤器与身份还原

身份还原由两个组件协作完成。自定义过滤器继承一次请求过滤一次的基础类，从授权头中取出 Bearer 令牌，交给认证服务校验。认证服务先做格式校验，要求令牌满足四十三位 URL 安全字符集合的正则，明显畸形的输入不必进入数据库查询；格式通过后计算摘要，用一条联表查询同时校验四件事：摘要存在、会话未被撤销、会话未过期、用户状态为 1。查询命中后，过滤器把用户对象放入安全上下文，并附加一个以角色码为后缀的权限标识。安全配置声明为无状态，关闭了表单登录、基本认证与跨站请求伪造防护，只放行登录与健康检查两个路径，其余请求一律要求已认证；未认证时由入口点直接返回状态码 401 与一段固定的 JSON 提示，而不是重定向到登录页，以便两个客户端都按统一方式处理。

4.2.3 会话使用时间的写入控制

每次校验令牌都更新最近使用时间会产生一次额外的写操作，在高频轮询的页面上会放大数据库压力。实现上增加了时间窗判断：只有当最近使用时间早于当前时间五分钟以上时才更新。这一处理牺牲了分钟级的精度，换取了写次数的显著下降，对“显示上次使用时间”这类需求已经足够。

4.2.4 用户上下文的传递

控制器方法通过参数注解直接取得当前用户对象，再从中取出用户编号传给服务层。服务层与仓储层的每个方法签名都以用户编号为第一个参数，形成编译期可见的约束：任何一处漏传用户编号，方法签名就无法通过。这一设计把“数据归属”从文档约定变成了类型约束。

4.3 记账模块的实现

4.3.1 新增与字段归整

新增接口在服务层补三件事：来源类型固定写入“手动”，不接受客户端指定；分类名称去首尾空格后写入；其余可空文本字段在为空串或仅含空白时统一转为空值，避免库里同时存在空串与空值两种表示，使后续按空值筛选失效。插入语句使用主键回填，插入成功后按主键重新查询一次并返回完整记录，使客户端拿到的是数据库生成的时间戳，而不是应用层的猜测值。控制器把该接口的成功状态码设为 201，并在响应体中返回完整记录。

4.3.2 分页查询的边界处理

列表接口在服务层对四个输入做归一化：页码下限为一、上限为一百万，每页条数下限为一、上限为一百，缺省页码为一、缺省条数为二十。日期范围缺省时，用一千零一年一月一日与九千九百九十九年十二月三十一日代替空值，使 SQL 不必拼接条件分支。排序字段依次为发生日期、发生时间与主键，三级降序保证同一天内多条记录的顺序稳定。是否包含已作废记录由一个布尔参数控制，实现上只切换状态过滤片段，其余语句不变。

4.3.3 汇总接口的必要性

汇总接口执行一条语句，用条件聚合同时算出笔数、支出合计与收入合计，并用合并空值函数保证无记录时返回零而不是空。该语句固定附加状态为 1 的条件，因此与列表接口的筛选口径可以不同。这一分离是设计阶段针对“分页累加导致总额少算”的直接修正：在手机首页只取一百条的旧实现中，超过一百笔后总额会偏小，改为服务端汇总后该问题不再出现。

4.3.4 作废与并发冲突

作废的校验分三层。第一层在服务层判断原因文本非空且不超过二百字，不满足直接返回参数错误。第二层先按主键查出记录，若记录不存在或用户编号不匹配，返回“未找到”；若记录状态已不为 1，返回“已作废”。第三层执行条件更新，更新语句同时限定主键、用户编号与状态为 1，并设置作废原因与作废时间；当受影响行数为零时，说明在第二层与第三层之间记录被其他请求抢先作废，此时同样返回“已作废”。控制器把“未找到”映射为 404，把“已作废”映射为 409，成功则返回更新后的记录。三层校验中第三层是关键：只做前两层查询再无条件更新，就会出现两次作废都返回成功、但只有一次真正生效的假象。

4.3.5 异常映射

记账域配置了一个只作用于该域控制器的异常通知类。参数校验失败时，取第一个字段错误的提示文本返回，而不是拼接全部错误，避免前端提示过长；服务层抛出的状态异常统一映射为 400 并回传原因文本。异常处理按业务域隔离，使其他域的响应格式不受影响。

4.4 日志与训练模块的实现

4.4.1 事务与组次约束

新增日志的方法标注了事务注解，日志主表与组次表在同一事务内写入，任一步失败整体回滚，不会留下只有主记录没有组次的半条数据。写入前有三条前置校验：文字记录不得携带组次，训练记录至少携带一组，每组必须填写次数或时长之一。这三条校验把“记录形式”与“数据形态”绑定起来，防止出现形式为文字却带训练明细的矛盾数据。未填写的数值保持为空而不是补零，是为了区分“做了但没记”和“确实为零”。

4.4.2 查询与类型过滤

列表接口校验日期范围的先后顺序，并校验记录形式只允许两种取值，其余取值返回参数错误。每页条数上限设为五十，比记账模块的一百更严，原因是日志正文较长、单条返回体更大。分页与计数的语句共用同一组过滤条件，保证总数与当前页数据来自同一口径。

4.4.3 真实样本导入

日志模块的数据来源之一是既有原型中以 Markdown 保存的每日生活记录。导入脚本先以只读方式计数，再逐行写入，并为每行生成来源标记；来源标记上建有唯一约束，源文件未变化时重复运行会跳过已导入的行。导入过程不修改原始文件，也不生成含私人内容的中间文件。导入结果为十天的记录共一百八十四条，其中睡眠三十六条、饮食三十三条、运动二十条，其余为日程、消费与其他类别。需要说明的是，所有原始行均以文字记录形式暂存，包括类别为“运动”的行：原文可能是训练计划、休息说明或区间次数，不能据此推断一次已完成的训练，更不能凭描述补造组次数据。这一取舍在论文中属于口径问题而不是实现缺陷。

4.5 身体健康模块的实现

4.5.1 体重与体成分

新增接口要求体重、体脂率、肌肉量三者至少填写一项，全部为空时返回参数错误。这一约束的目的是防止产生一条没有任何测量值、只有日期的空记录，使趋势图出现无意义的断点。

4.5.2 睡眠记录与一致性校验

睡眠记录保存总时长与深睡、浅睡、快速眼动三段时长。写入前把三段时长求和，与总时长比较，允许五分钟的容差，超出则拒绝。容差的存在是因为设备上报的分段与总时长本身可能存在舍入差异，严格相等会把正常数据判为非法。查询接口在未给日期时默认返回最近九十天，并限制一次查询跨度不超过三百六十六天，既保证默认视图有内容，也避免一次请求拉取全部历史。

4.6 双端客户端的实现

4.6.1 Web 端的状态机与并发处理

Web 端没有引入路由库，页面切换由一个状态变量控制：初始为检查中，令牌存在且校验通过则进入就绪态，否则进入登录态。就绪态下按侧栏的当前分区渲染内容，分区配置是一个数组，每一项带就绪标记，尚未实现的日程课表与附件归档被标记为未就绪，在界面上以说明文字呈现而不能点击进入，从而避免把未完成的模块做成可操作的入口。

接口调用统一由一个封装函数完成，该函数做了两件事：一是用中断控制器设置十秒超时，超时后中断请求，使界面不会无限等待；二是把非成功响应统一转换成带状态码的错误对象，页面据此区分“用户名或密码错误”“连接超时”“服务端未运行”三种提示。令牌存放在会话存储而非本地存储，关闭标签页即失效，以此降低共用电脑上的遗留风险。

列表页存在一类典型问题：用户快速切换筛选条件时，先发出的请求可能后返回，覆盖掉新结果。实现上为每个列表维护一个自增的请求编号，响应返回时比对编号，过期响应直接丢弃。退出登录时同时递增所有列表的编号并清空数据，防止上一个账号的数据残留到下一个账号的界面上。

4.6.2 Android 端的页面组织与网络层

Android 端在配置文件中注册八个页面，并把导航栏样式统一设为自定义，导航栏由页面自身绘制，以匹配设计系统给定的配色。服务地址与令牌键名集中在一个常量文件里，文件顶部注明当前地址仅用于真机调试，需配合端口反向转发把手机的本地端口映射到开发机，正式打包前必须改为 HTTPS 域名。

登录页在加载时先读取本地令牌，若存在则调用当前用户接口探测有效性：有效则直接跳转首页，无效则清除本地令牌停留在登录页。这一处理让用户再次打开应用时不必重新输入密码，同时保证失效令牌不会残留在本地。网络请求使用平台提供的请求接口与回调式写法，未引入额外的请求库，与工程为零依赖的策略一致。

4.7 智能工具接口的实现

该模块目前只有一个只读接口，接收月份参数，返回该月的训练次数、有效账目笔数、收入与支出合计。实现上有三点值得说明。其一，方法标注为只读事务，从声明上排除了写入的可能。其二，月份解析失败与年份越界分别返回不同的参数错误提示，前者由年份月份解析异常捕获，后者显式判断年份区间，避免异常堆栈直接暴露给客户端。其三，汇总逻辑不重复实现，而是复用记账模块的汇总方法与日志模块的计数方法，因此工具接口的口径与两个业务页面必然一致，不会出现同一月份在两处显示不同金额的情况。之所以只做只读而不提供写入，是因为模型输出需要用户确认后才能落库，写入路径必须与手工录入共用同一套校验，这一约束在设计阶段就已确定。

4.8 本章小结

本章说明了设计在三个工程中的落地方式。服务端以业务域分包、以用户编号为方法签名的第一参数，把手写的 SQL 与手写的行映射控制在可维护的规模内；认证用随机令牌加摘要存储代替自签名令牌，并通过用户行排他锁解决并发登录的会话数量竞争；记账模块用条件更新与受影响行数检查解决并发作废，用独立汇总语句解决分页统计偏差；日志模块用事务保证主表与组次的原子性，用来源标记保证导入幂等；两个客户端分别采用状态机与配置文件驱动的页面组织，并在 Web 端额外处理了响应乱序这一实际遇到的问题。下一章将对上述实现进行测试验证。
