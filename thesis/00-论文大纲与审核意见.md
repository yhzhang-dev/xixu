# 论文大纲与审核意见（v1，2026-11-01）

本文件按“理工科系统实现型本科毕业论文”的标准对现有素材做一次审核，并给出可直接用于开题报告的章节大纲。审核依据为仓库内实际代码与文档，不采用《选题意向-初稿》中的规划口径。

## Part 1 技术缺陷（Technical Defects）

### 缺陷一：题目副标题与系统实际能力不符，这是最硬的问题

初稿题目为“个人生活数据管理系统的设计与实现——以自然语言与图像识别为录入方式”。但当前服务端只有 `AssistantToolController` 提供的 1 个只读接口 `GET /api/assistant/tools/monthly-snapshot`，代码中不存在任何大模型调用、提示词组装、OCR 或置信度处理；`docs/日志与训练接口说明.md` 第 41 行亦明确写着“模型接入及自动工具选择尚未实现”。

后果是：论文题目承诺了自然语言与图像识别，正文却无法给出对应实现与测试，评阅时会被直接判定为“题目与内容不符”。必须在以下两条路中选一条，并在开题前定稿。

1. 改副标题，使题目与已交付能力一致。例如“个人生活数据管理系统的设计与实现——账务、日志与健康记录的统一建模与多端实现”。
2. 保留副标题，但在第八学期第 7 周前真正实现“一句话记账”的最小闭环（受控 Schema 解析 + 置信度阈值 + 失败退回表单），并把自然语言处理作为第 4 章的一节而非全部。

建议取第 1 条，理由见缺陷三。

### 缺陷二：技术路线章节若照抄初稿，会与代码逐项冲突

初稿第三章写明 Android 用 Kotlin + Jetpack Compose + MVVM + Hilt + Room + Retrofit，服务端用 MyBatis-Plus + JWT，数据库加 Redis，后台用 Element Plus + ECharts，附件上对象存储，部署用 Docker Compose。实际代码为：

| 初稿声称 | 代码实际 | 依据 |
|---|---|---|
| Kotlin + Compose + Hilt + Room | uni-app（Vue 3）单页应用，8 个 `.vue` 页面 | `android/pages/` |
| MyBatis-Plus | 未引入；仅 `spring-boot-starter-jdbc`，用 `JdbcTemplate` | [pom.xml](../server/pom.xml) 第 34–54 行 |
| JWT | 自研 32 字节 `SecureRandom` 令牌，SHA-256 摘要存 `auth_session` 表，有效期 86400 秒，单用户最多 5 个活跃会话 | [AuthService.java](../server/src/main/java/wiki/yuhang/xixu/auth/AuthService.java) 第 38–48 行 |
| Redis | 未使用 | 开发环境文档“暂时不用下载”一节 |
| Element Plus + ECharts + TypeScript | 仅 `vue` + `vite`，无 UI 库、无图表库、无 TS | [package.json](../admin/package.json) |
| 对象存储 OSS/COS | 无，附件模块尚未开始 | 无对应代码 |
| Spring Boot 3 | Spring Boot 4.1.2 | `pom.xml` 第 8 行 |

论文的技术选型章节必须按“实际采用的技术”重写，并把“为什么不用 MyBatis-Plus / JWT / Redis”写成有依据的取舍（数据量小、单表操作为主、无水平扩展需求），这本身就是合格的工程论证；照抄初稿则属于虚构。

### 缺陷三：工作量与实际范围严重不匹配，缺 P0 模块

初稿把“账本管理、日程与课表、系统管理、数据层”列为 P0 及格线，但仓库中没有课表、日程、角色权限、数据字典、操作审计的任何代码：数据库脚本里没有 `course`、`course_session`、`schedule_event`、`role`、`user_role`、`menu`、`operation_log`。已真实建表并接入接口的只有 5 张。

反过来，初稿未列入 P0 的两个模块反而做完了：日志与训练（含 184 条真实样本导入）、身体健康数据（`/api/wellness` 的体重与睡眠接口）。

所以第 3 章功能设计不能按初稿的十一个模块平铺，必须收敛为四个已实现模块加两个预留模块，并说明收敛理由（个人独立开发、第 7 周功能冻结）。范围收缩不写清楚，工作量会被判为不足；写清楚，则“按优先级增量交付”本身就是可写的研究内容。

### 缺陷四：创新点有四条缺乏代码支撑

初稿第五章的五个难点中，“离线优先与增量同步”“历史数据迁移与逐笔比对脚本”在仓库中找不到实现；真正存在的是“软删除 + 作废原因留痕”“服务端统一汇总避免分页累加错误”“会话令牌摘要存储与并发作废 409 返回”。论文的“重点与难点”一节应改为后者，用代码位置和测试用例支撑，不能沿用规划文本。

### 缺陷五：缺少可复现的实验与测试章节

现有测试为 5 个测试类、23 个 `@Test` 方法（289 行），覆盖认证、记账、日志、健康、智能工具五个服务；另有 `test-login-local.ps1`、`test-ledger-local.ps1` 等真实接口联调脚本，以及“手机新增 → Web 查看 → Web 作废”的跨端人工验收记录。这些是第 5 章的全部证据来源，目前尚未成文。测试章节需要给出：测试环境、用例设计方法、单元测试统计、跨端验收步骤与结果、以及未被覆盖的部分（如并发作废、跨用户越权）。导入工具另有 2 个 Python 单元用例（`server/tools/test_import_dsh_logs.py`），应一并计入。

### 缺陷六：图表资产不足

论文至少需要 6 类图：系统总体架构图、功能模块图、E-R 图、核心业务流程图（记账新增与作废）、时序图（登录鉴权）、界面截图。目前 `design/` 只有 1 段 mermaid 架构草图和 3 张真机截图，`database/08-身体健康与日志分类设计.md` 里有一段 13 个实体的 mermaid ER 草图但对应 SQL 未执行。

### 缺陷七：命名与口径不统一

系统名“汐序”、论文名“个人生活数据管理系统”、一级模块“身体与训练 / 日志 / 记账”、表名前缀 `life_log_` 与 `health_` 并存。论文中需固定一套术语表，避免同一对象在摘要、正文、图表中出现三种叫法。
