# 01 · 用户表设计草案

状态：用户于 2026-10-31 报告已在本地 MySQL 执行，`SHOW TABLES` 显示 `app_user`、`SELECT COUNT(*)` 为 0；本次未直接连接数据库复核。首期假设允许多个用户，各人的账目、日程、日志和附件通过 `user_id` 归属本人。

## 先确定的业务规则

1. 首期用**用户名 + 密码**登录，不收集邮箱或手机号；暂不做公开注册与找回密码。
2. 只有 `ADMIN`（管理员）和 `USER`（普通用户）两种固定角色，放在用户表的 `role_code` 字段。暂不建角色、权限和用户角色关联表。
3. 普通用户在 Android 和 Web 两端都能读写自己的业务数据。管理员可管理账号状态；**管理员身份不默认授权查看别人的私人账目、日志和附件**。“Web 管理端”不等于“只能由管理员使用”。这些规则需要服务端按当前登录用户执行，不能仅靠前端隐藏按钮。
4. 新账号默认 `USER`；客户端不能自行提交 `ADMIN` 角色。管理员账号只在受控的初始化流程中创建。
5. 密码只由服务端用可靠的密码哈希算法处理，表中仅保存哈希值，不保存明文、可逆密文或快速 SHA-256 摘要。

## 字段

| 字段 | 类型 | 约束 | 用途 |
|---|---|---|---|
| `id` | `BIGINT UNSIGNED` | 主键、自增 | 内部用户标识，其他业务表以此关联 |
| `username` | `VARCHAR(50)` | 非空、唯一 | 登录名；首期不允许修改 |
| `password_hash` | `VARCHAR(255)` | 非空 | Spring Security 编码后的密码哈希 |
| `display_name` | `VARCHAR(50)` | 非空 | 页面展示名，可以修改 |
| `role_code` | `VARCHAR(16)` | 非空，`ADMIN` / `USER` | 固定两级角色，默认 `USER` |
| `status` | `TINYINT UNSIGNED` | 非空，0 / 1 | 0 禁用，1 正常 |
| `created_at` | `DATETIME(3)` | 非空 | 创建时间 |
| `updated_at` | `DATETIME(3)` | 非空 | 最后修改时间 |
| `last_login_at` | `DATETIME(3)` | 可空 | 最近一次成功登录时间 |

## 建表 SQL 草案

```sql
CREATE TABLE app_user (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '用户 ID',
    username VARCHAR(50) NOT NULL COMMENT '登录名',
    password_hash VARCHAR(255) NOT NULL COMMENT '密码哈希',
    display_name VARCHAR(50) NOT NULL COMMENT '展示名',
    role_code VARCHAR(16) NOT NULL DEFAULT 'USER' COMMENT 'ADMIN 或 USER',
    status TINYINT UNSIGNED NOT NULL DEFAULT 1 COMMENT '0 禁用，1 正常',
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
        ON UPDATE CURRENT_TIMESTAMP(3),
    last_login_at DATETIME(3) NULL DEFAULT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_app_user_username (username),
    CONSTRAINT chk_app_user_role CHECK (role_code IN ('ADMIN', 'USER')),
    CONSTRAINT chk_app_user_status CHECK (status IN (0, 1))
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci
  COMMENT='系统用户';
```

## 后续表如何引用

记账、日程、日志和附件表各自包含 `user_id BIGINT UNSIGNED NOT NULL`，指向 `app_user.id`。删除用户、是否保留历史记录、是否需要外键级联删除，等设计完整数据模型时决定；当前不直接执行删除。

## 需要在接口阶段落实

- 登录接口按 `username` 查用户，检查 `status=1` 后验证密码哈希。
- 所有业务查询均按当前登录用户的 `id` 限定数据范围；不要信任客户端传来的 `user_id`。
- 密码哈希算法与参数在 Spring Security 实现时确定；不要自己编写哈希算法。
